Updated September 11, 2026 (Pacific). **Local phase-two implementation is explicitly approved and implemented with the all-staff app/shop read option configurable and default OFF.** Jeffrey has now approved all cashiers viewing shop-scoped balances/history through the implemented all-staff approved-app/shop policy, with corrections restricted to existing authorized Ops controls. He also approved read-only Shopify setup inspection, handled by the parent in the browser. This settles the read-access policy; it does not enable runtime flags or authorize native testing, installation or production access. Individual Ops bindings and extra staff login are outside this implementation; restricted-role alternatives below remain available for a later design if needed. Deployment, app setup, installation, credentials, subscriptions and activation remain separate gates. See [local implementation and verification](phase-two-runbook.md).

## Problem and outcome

Staff should see an existing customer's earned balance and recent point history within native POS, without copying an internal customer/order ID into Ops. The phase-one ledger remains the accounting authority. Viewing points must never create an account, award points, trigger a canonical fetch, enqueue a webhook/replay, change a customer, or alter checkout.

The implemented entry point is a customer-details balance block with a **View history** action opening its companion modal. Staff find or attach the existing profile using native POS. Customer selection, contact lookup and identity management remain Shopify's responsibility. No customer name, email, phone or address is requested or replicated by this extension.

## Current source and limits

The worktree has `app/loyalty/models.py`, `service.py`, `ops.py`, `access.py`, and the actual `/loyalty` routes/template. Balance is derived from the existing immutable ledger; exceptions, corrections and replay already live in Ops. `app/routers/loyalty.py` authorizes current Ops cookie sessions against `User` and explicit permission grants. That cookie authorization is not a Shopify ID-token verifier.

Before phase two, this checkout had no Shopify app/extension TOML, Node package, or POS token verifier. It now has the isolated `extensions/loyalty-pos/` package, two native entry points, `pos_auth.py`, `queries.py`, and a dedicated bearer router. There is still no parent Shopify app configuration or real extension UID. The shared Shopify transport remains pinned to Admin API `2026-04`; no individual Shopify-user-to-Ops binding was added. Do not transplant the unrelated TikTok OAuth flow or expose Ops HTML through an unauthenticated iframe. Actual installed app type, app ownership, scopes, POS plans and device versions remain uninspected.

## Scope and staff experience

- Show integer balance, last successful check, and clear paused/review information for the viewed customer. Do not call points money, savings, credit or redeemable value.
- Open recent ledger history: date, purchase/refund/administrator adjustment and signed whole-point change. Use dollar formatting only for any approved eligible-merchandise context. Raw GIDs, revisions, JSON, case references and operator identities stay out of the POS view.
- Distinguish no posted history, unavailable service, permission denied, identity review and stale accounting. A fetch failure is never displayed as zero points. An unknown local customer is a read-only “No posted points yet” result, with no account creation.
- Refresh on open and explicit retry. Clear state and cancel/ignore outstanding responses on customer, authenticated session, shop or staff change. No persistent local balance cache; offline state does not invent current points. After a purchase, show only previously posted ledger points until phase-one processing catches up.
- Keep corrections, attachment attestations, reconciliation and identity resolution in Ops with their existing permissions and audit trail.

No earning changes, event handlers that award points, redemption, discounts, rewards, contact replication, marketing, customer-facing display, receipt customization, Smile changes or Shopify mutations. A home-grid/cart shortcut is deferred unless the customer-details flow is insufficient during review; it adds context-switch cases without changing accounting.

## Authentication and authorization — cashier read policy approved, runtime disabled

A token proves the shop/app/authenticated principal. It does **not** attest the selected customer, active PIN staff or reported location/device. A submitted customer or staff ID cannot become an authorization credential.

Every access option validates a bounded bearer token against the explicitly configured extension app and derives the shop from verified claims. Each read checks the approved access policy and its revocation state. Shop and customer identity are included in every ledger query; the caller cannot select another shop. Individual Ops bindings and user grants apply only if Jeffrey selects a restricted-role policy; they are not prerequisites for the all-staff option below.

Decision recorded September 11: Jeffrey approved the first approach for all cashiers to view balances/history, with corrections restricted in Ops. It grants shop-scoped individual reads through the approved app/shop authenticated session without individual Ops bindings or extra login. Actual app/shop setup and runtime activation remain separately gated. The other approaches are retained only as alternatives if a future policy restricts individual roles; they are outside this implementation:

| Approach | Security boundary and consequence |
|---|---|
| Explicitly authorize all staff using the approved POS app/shop to view balances/history | Enforce the explicit all-staff read policy through a verified app/shop/authenticated session and shop-scoped queries. No individual Ops binding or extra staff login is required. PIN identity is not an authorization boundary and must never be claimed verified; the token authenticates the logged-in Shopify user, not each cashier. This option intentionally grants the same read access to all staff using that approved session. Missing/invalid tokens or an unapproved app/shop still deny access. |
| Restrict initial access to individually authenticated Shopify users with explicit Ops bindings | Verifies that authenticated principal. It does **not** securely authorize a different person sharing that login through a PIN. Shared-login/PIN-only workflows must remain unsupported unless a separately approved staff-proof mechanism is added. A client-side equality check alone cannot enforce this restriction against a modified client. |
| Add separate staff authentication to Ops for shared-device use | Candidate: short-lived, revocable Ops authorization paired to the verified Shopify shop/app/session and an explicitly bound Ops staff account. This proves an Ops principal, not inherently Shopify's active PIN. Credential handling, pairing/return UX, session lifetime, PIN-switch revocation and whether this boundary is acceptable need a focused security design before code. Do not collect or attempt to verify Shopify PINs. |

**Approved decision:** all cashiers may view balances/history through the all-staff approved-app/shop policy, without individual Ops bindings or extra login. This is Jeffrey’s explicit policy grant, not inferred inheritance of an owner’s permissions or proof of a cashier’s PIN identity. It does not grant Ops correction permissions. If a future policy restricts individual roles, retain the per-user binding or separate Ops authentication options. Bindings map `(app client ID, shop, authenticated Shopify user ID)` to an active Ops user by explicit administrator action, never contact matching or role inference. If a restricted policy requires cryptographic proof of the currently PIN-selected staff, no supporting attestation was established in the reviewed standard APIs; remain blocked rather than accepting unsigned `staffMemberId`. Administrator corrections stay in Ops under their existing permissions in every option; no bulk or contact queries are added.

The approved recommendation permits an authenticated session authorized for the configured app/shop to read this shop's individual loyalty balances/history, with the UI supplying the native selected customer. This matches the current authorized Ops lookup capability. The API cannot prove native selection from an arbitrary submitted ID. A stricter selected-customer-only security rule needs additional supported evidence before implementation. No bulk/search endpoint or contact lookup is proposed.

## Implemented technical contract

A distinct, default-OFF POS read gate exists independent of receiving/processing/posting. It requires schema readiness, approved extension app/shop binding and enforcement of the selected access policy. Paused posting may still expose an explicitly stale balance; a missing schema must return unavailable.

The `GET /api/loyalty/pos/customers/{customer_id}` returns only a shop-scoped ledger snapshot: whole-point balance, freshness/review labels, a bounded history page and opaque cursor. Validate positive safe integer customer IDs before converting them to GIDs; reject unsafe JavaScript numbers. Use one SQL statement for each consistent balance/history snapshot, with a signed watermark for later pages. Signed count/sum checks detect lower-ID rows that commit late and require refresh. Whole points travel as decimal integer strings to preserve values beyond JavaScript’s safe integer range; they are never fractional points. Bind history cursors to shop/customer/watermark; cap page size at 25 (the UI requests 10). No contact or general customer existence fetch is needed; absence of a local account is not a Shopify identity validation claim.

Keep bearer auth separate from Ops cookie auth. Do not relax existing CSRF routes or accept an Ops cookie as fallback on this API. Use HTTPS, no-store responses, bounded tokens/request sizes, conservative request limits, sanitized failure codes and no token/customer payload logging. Do not rely on CORS or client headers for identity. Any approved account-binding/authorization mutations remain in the authenticated Ops admin surface with CSRF and AuditLog. New settings and bindings start unset; no real app IDs or secrets belong in source.

## Verification, release and rollback

Acceptance requires native customer context with no typed IDs; the same balance/history as Ops at a fixed ledger watermark; no database accounting writes across repeated opens/retries; and rejection of forged, wrong-app, wrong-shop, expired or revoked principals. Exercise missing token, null customer, unsafe numeric IDs, cross-customer cursors, out-of-order responses, staff/session/customer switching, no history, refunds, holds, offline mode, timeouts and paused processing. For the all-staff option, test that an approved authenticated app/shop session can read without an individual Ops binding or extra login, and that reported PIN identity neither grants nor restricts that read access or appears as verified identity. For restricted-role options, test explicit denies even for manager/admin roles. Verify tokens never appear in URLs, logs, screenshots or persistent storage.

Local component and API tests can use synthetic contexts and signed test tokens without Shopify access. Real POS preview is a later gate: the official workflow uses a Partner account, development store, CLI and iOS/Android POS. `shopify app dev` connects the development store and normally creates a tunnel; QR/mobile preview runs code in POS. It is not a localhost-only operation and was not executed. A simulator/device may need a reachable development backend. [Getting started](https://shopify.dev/docs/apps/build/pos/getting-started), [Development server communication](https://shopify.dev/docs/apps/build/pos/communicate-with-server)

A browser mock cannot validate native rendering, session-token claims or PIN behavior. Require separately authorized synthetic development-store tests on actual POS before any production review. Deploying the backend, releasing an app version, installing it and enabling target locations each require concrete review and authorization.

Rollback disables the POS read gate and removes/disables extension placement through separately authorized operations. It preserves the ledger and all phase-one accounting flags. Reverting UI/backend code never deletes accounts, changes balances, migrates identities, or rewrites history. Security defects disable the read/policy gate or revoke the app session through a separately approved procedure. There is no individual binding to revoke in this implementation. Locally verified tokens remain usable until expiry (accepted lifetime at most five minutes); online revocation introspection is not implemented.
